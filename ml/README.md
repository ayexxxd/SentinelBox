# SentinelBox health model

A small neural network (MLP 5-16-8-3, 259 float32 params, ~1 KB) that runs on the
ESP32 and classifies each 2 s reading as `NORMAL`, `WARNING` or `MAINTENANCE`. It replaces
the weighted-score rule from the main README.

```bash
pip install -r requirements.txt
python download_data.py   # UCI fan accelerometer (3.6 MB); LBNL only with --lbnl (530 MB)
python build_dataset.py   # -> data/processed/{train,test}.npz
python train.py           # trains (+ data/real if present), evaluates, writes ../SentinelBox/sentinel_model.h
```

`train.py` also compiles `SentinelBox/sentinel_ann.h` with gcc and checks that
the C inference gives the same result as the Python model.

## Inputs: relative to the unit's own baseline

The ESP32 first learns this unit's normal operation (45 readings, 90 s). After that the
network sees how far each signal has moved from the baseline, never absolute values:

| Input | Formula | Sensor |
|---|---|---|
| `vib_rms` | log2(RMS / baseline) | MPU6500, 100 samples at 50 Hz, axis means removed |
| `vib_crest` | log2(crest / baseline) | peak / RMS: impacts, looseness |
| `vib_kurt` | log2(kurtosis / baseline) | impulsiveness |
| `current` | log2(I / baseline) | INA219 |
| `temp` | (T − baseline) / 5 °C | MAX6675 |

This makes the model independent of fan size, speed and sensor mounting, so a network
trained on a lab fan still works on our fans once they have learned their baseline. To
adjust it to the prototype, record labelled readings and retrain. The thresholds are
constants at the top of `build_dataset.py`.

## Data

| Signal | Source | Kind |
|---|---|---|
| Vibration | [UCI Accelerometer](https://archive.ics.uci.edu/dataset/846/accelerometer): a 12 cm cooling fan with weights on its blades, 3 imbalance configurations × 17 speeds, 50 Hz | **real** |
| Current | Bands from [LBNL FDD, fan coil unit](https://data.openei.org/submissions/5763), see `calibration/lbnl_fcu_fan_power.csv`: fan power ×1.02–1.05 for minor faults, ×1.08–1.10 moderate, ×1.24–1.29 severe | synthetic, calibrated |
| Temperature | +3 to 6 °C warning, above +6 °C maintenance (the demo hair dryer gives +8 to 10 °C) | synthetic |

Vibration labels follow the physics: the imbalance force is proportional to m_eff·ω²
(red config 2m, blue config √2·m, green config balanced). Below 40 % speed the
unbalanced configs vibrate like the healthy one, so those windows are not used as faults.
Each sensor is faulted independently, plus 10 % of samples with several sensors faulted
at once.

## Results (test set: fan speeds 45/65/85 % never seen in training)

| KPI | ANN | Previous rule |
|---|---|---|
| Detection rate | 1.000 | 0.965 |
| False alarm rate | 0.003 | 0.000 |
| Missed anomaly rate | 0.000 | 0.035 |

Overall accuracy is 99.4 %. The current and temperature labels come from bands that we
defined ourselves, so the network essentially relearns those thresholds. The number that
really shows it generalises is vibration on unseen speeds (99.3 %). These metrics describe
the lab data. The real KPIs come from the prototype recordings (see below): every recorded
window also stores what the model predicted.

## On the ESP32 (SentinelBox gateway)

The network runs in the gateway, `SentinelBox/SentinelBox.ino` (Arduino IDE, core ESP32
only, no extra libraries). The HVAC nodes (`HVAC01/`, `HVAC02/`) send current and
temperature over UART; the gateway measures vibration with its own MPU6500. Copy
`SentinelBox/secrets.example.h` to `secrets.h` (git-ignored) and fill in WiFi and the
server IP.

- `sentinel_ann.h`: features and inference in plain C.
- `sentinel_model.h`: the weights, generated by `train.py`.
- Every 2 s the gateway takes 100 MPU samples at 50 Hz without blocking. The UART keeps
  draining in between. It averages the current and temperature the connected HVAC sent
  during those 2 s, runs the network, and POSTs one reading to `/api/readings`.
- Each `unit_id` learns and keeps its own baseline in NVS (45 windows, 90 s), so you can
  swap HVACs plug-and-play. Serial `r` relearns the connected unit. While a unit is
  learning, `status` and `health_pct` are sent as null.
- The 3-of-5 persistence decides `status` (`healthy` / `degraded`). A WARNING prediction
  shows only as a lower `health_pct`.
- `health_pct` is smoothed twice. The softmax runs at temperature 3 (the class does not
  change), which gives a gradual curve instead of 100/55/10 jumps. An EMA over time then
  smooths it further, and the value is rescaled so that the learned baseline reads 100 %.
- `vibration` is sent in mm/s, estimated as a_rms / (2π·f_rot). The speed comes from
  `fanRpm()` in the sketch, set per unit (measure it). This assumes the vibration is
  dominated by the 1× rotation frequency, as with imbalance. The network itself works on
  the acceleration ratios.
- If a sensor reports null (or never reported), the network sees it at its baseline.
- The serial monitor shows the per-sensor scores (vibration / current / temperature): how
  much health is lost when only that sensor deviates. This tells the technician *why* the
  alert fired.
- Imbalance barely shows at low speed; in the UCI data it is not measurable below ~40 %.
  HVAC-01 runs at 10 % PWM, so on that unit expect vibration to react much less than
  current and temperature.

## Live view (no recording)

```bash
python monitor.py                      # first /dev/ttyUSB* or /dev/ttyACM*
```

Plots health, current, temperature and vibration per `unit_id` from what the board prints.
On the gateway these are the `TX {...}` lines, the JSON it POSTs every 2 s; on an HVAC
node they are the `LINK> {...}` lines. It also echoes every line to the terminal and sends
what you type to the board: `r` relearns, `v` shows the raw UART lines on the gateway, and
on an HVAC node a number 0–100 sets the fan speed. Close the Arduino serial monitor first.

**Ubuntu: the ESP32 is detected but no `/dev/ttyUSB0` appears.** The `brltty` package
(braille displays) grabs CH340/CP210x adapters. Remove it once:

```bash
sudo apt remove brltty
```

If `dialout` is not in `groups`, also run `sudo usermod -aG dialout $USER`, then log out
and back in.

## Building the real dataset (prototype)

The public data teaches the network what "moving away from normal" looks like. Recordings
from our own fans adjust it to our sensors and mounting. Each 2 s window becomes one row.

**What gets recorded.** After the baseline is learned, the firmware prints one `CSV,...`
line per window on the serial port. The line holds the raw features (vibration RMS, crest,
kurtosis, current, temperature), the baseline, and what the model predicted.
`collect_serial.py` saves those lines to `data/real/<session>_<scenario>_L<label>.csv`,
together with the label you pass it. The dashboard does not store crest or kurtosis, so
record over serial, not from the API.

### 1. Prepare the hardware

1. Screw or glue the MPU6500 rigidly to the fan housing. Always use the same spot and
   orientation; tape or a loose mount adds its own vibration.
2. On each HVAC node, put the INA219 in series with the fan supply, and place the MAX6675
   thermocouple on the motor or housing.
3. Set each fan's real speed in `fanRpm()` in `SentinelBox.ino` (used only for the mm/s
   shown on the dashboard).
4. Flash `HVAC01` / `HVAC02` and the `SentinelBox` gateway. Connect the gateway over USB,
   then close the Arduino serial monitor: only one program can hold the port.
   `collect_serial.py` reads the **gateway's** port.

### 2. Learn the baseline

5. Let the fan run normally for at least 5 min so the temperature settles.
6. Send `r` over serial, or start with an empty NVS, and let it learn for 90 s without
   touching anything.
   The gateway stops printing `aprendiendo n/45` and starts printing `CSV,` lines.

### 3. Record each condition

Run one command per session. Use `--skip` to throw away the transition, so for example
you are not recording the dryer while it is still heating the fan up. Between faulty
sessions, go back to normal and wait until health returns to around 100.

```bash
python collect_serial.py --port /dev/ttyUSB0 --label 0 --scenario normal --seconds 300
```

| # | Condition | How to produce it | `--label` | Duration |
|---|---|---|---|---|
| 1 | Normal | Nothing, fan running | 0 | 5 min |
| 2 | Tricky normal | Tap the table, walk by, plug in chargers nearby, move the cables | 0 | 3 min |
| 3 | Mild heat | Hair dryer 40–50 cm away (+3 to 6 °C) | 1 | 2 min, `--skip 30` |
| 4 | Strong heat | Hair dryer 10–15 cm away (above +6 °C) | 2 | 2 min, `--skip 30` |
| 5 | Mild imbalance | A small bit of putty or tape (~0.2 g) on one blade | 1 | 3 min |
| 6 | Strong imbalance | More mass (~1 g) or two pieces on the same side | 2 | 3 min |
| 7 | Partially blocked airflow | Cardboard over ~30 % of the intake | 1 | 3 min |
| 8 | Heavily blocked airflow | Cardboard over ~70 % of the intake | 2 | 3 min |
| 9 | Combination | For example strong imbalance plus mild heat | 2 | 2 min |

Choose the label by the *intended* severity of the perturbation, not by what the model
says. If a perturbation does not measurably change the signal (for example, current stays
within ±3 %), label it 0 or leave it out: the network cannot learn something the sensors
do not see.

### 4. Repeat to cover the variation

7. Record the whole table on **both units**: plug HVAC-01 into the gateway, then HVAC-02.
   Each unit keeps its own baseline, and the CSV rows carry the `unit_id`.
8. Repeat on **at least two different days** or at different room temperatures, with a new
   baseline each time.
9. Aim for about 150 windows (5 min) per condition and unit. Every file is one session;
   more short sessions beat one long session.

### 5. Retrain and flash

```bash
python train.py
```

10. `train.py` picks up `data/real/*.csv` on its own and weights each real window 5×
    (`REAL_WEIGHT`). It holds out ~25 % of the sessions of each class as a test set and
    prints "Real prototype, held-out sessions", with the per-scenario accuracy and the KPIs.
11. Check the false alarm rate on held-out normal sessions (rows 1–2) and the detection
    rate on the perturbations. If a scenario fails, record more sessions of it.
12. `train.py` writes the new `SentinelBox/sentinel_model.h` directly; flash the gateway
    again. The baselines in NVS are kept.

### 6. Validate live

13. Every CSV row also stores the model's live prediction (`pred_cls`, `pred_health`).
    Comparing it with the `label` of the session gives the detection and false-alarm rates
    of the firmware as it is flashed, before retraining. The same recording therefore does
    two jobs: it is training data and a validation of the model already on the ESP32.
