# SentinelBox health model

A small neural network (MLP 5-16-8-3, 259 float32 params, ~1 KB) that runs on the
ESP32 and classifies each 2 s reading as `NORMAL`, `WARNING` or `MAINTENANCE`. It replaces
the weighted-score rule from the main README.

```bash
pip install -r requirements.txt
python download_data.py   # UCI fan accelerometer (3.6 MB); LBNL only with --lbnl (530 MB)
python build_dataset.py   # -> data/processed/{train,test}.npz
python train.py           # trains, evaluates, writes ../firmware/SentinelBoxANN/sentinel_model.h
```

`train.py` also compiles `firmware/SentinelBoxANN/sentinel_ann.h` with gcc and checks that
the C inference gives the same result as the Python model.

## Inputs: relative to the unit's own baseline

The ESP32 first learns this unit's normal operation (45 readings, 90 s). After that the
network sees how far each signal has moved from the baseline, never absolute values:

| Input | Formula | Sensor |
|---|---|---|
| `vib_rms` | log2(RMS / baseline) | MPU6500, 100 samples at 50 Hz, axis means removed |
| `vib_crest` | log2(crest / baseline) | peak / RMS: impacts, looseness |
| `vib_kurt` | log2(kurtosis / baseline) | impulsiveness |
| `current` | log2(I / baseline) | INA219 |
| `temp` | (T − baseline) / 5 °C | MAX6675 |

This makes the model independent of fan size, speed and sensor mounting, so a network
trained on a lab fan still works on our fans once they have learned their baseline. To
adjust it to the prototype, record labelled readings and retrain. The thresholds are
constants at the top of `build_dataset.py`.

## Data

| Signal | Source | Kind |
|---|---|---|
| Vibration | [UCI Accelerometer](https://archive.ics.uci.edu/dataset/846/accelerometer): a 12 cm cooling fan with weights on its blades, 3 imbalance configurations × 17 speeds, 50 Hz | **real** |
| Current | Bands from [LBNL FDD, fan coil unit](https://data.openei.org/submissions/5763), see `calibration/lbnl_fcu_fan_power.csv`: fan power ×1.02–1.05 for minor faults, ×1.08–1.10 moderate, ×1.24–1.29 severe | synthetic, calibrated |
| Temperature | +3 to 6 °C warning, above +6 °C maintenance (the demo hair dryer gives +8 to 10 °C) | synthetic |

Vibration labels follow the physics: the imbalance force is proportional to m_eff·ω²
(red config 2m, blue config √2·m, green config balanced). Below 40 % speed the
unbalanced configs vibrate like the healthy one, so those windows are not used as faults.
Each sensor is faulted independently, plus 10 % of samples with several sensors faulted
at once.

## Results (test set: fan speeds 45/65/85 % never seen in training)

| KPI | ANN | Previous rule |
|---|---|---|
| Detection rate | 1.000 | 0.965 |
| False alarm rate | 0.003 | 0.000 |
| Missed anomaly rate | 0.000 | 0.035 |

Overall accuracy is 99.4 %. The current and temperature labels come from bands that we
defined ourselves, so the network essentially relearns those thresholds. The number that
really shows it generalises is vibration on unseen speeds (99.3 %). These metrics describe
the lab data; the real KPIs come from running the prototype with `real_condition` tagged
(serial commands `n` / `p`).

## On the ESP32

`firmware/SentinelBoxANN/` (Arduino IDE, needs "Adafruit INA219" and "MAX6675 library").
Copy `secrets.example.h` to `secrets.h` (git-ignored) and fill in WiFi and the server IP.

- `sentinel_ann.h`: features and inference in plain C.
- `sentinel_model.h`: the weights, generated by `train.py`.
- The sketch learns the baseline, keeps it in NVS (serial `r` relearns it), runs the
  network and applies the 3-of-5 persistence. It drives the LEDs (green = normal,
  orange = maintenance) and POSTs readings to `/api/readings`. A WARNING prediction
  shows only as a lower `health_pct`; the status stays `NORMAL`.
- `health_pct` is smoothed twice. The softmax runs at temperature 3 (the class does not
  change), which gives a gradual curve instead of 100/55/10 jumps. An EMA over time then
  smooths it further, and the value is rescaled so that the learned baseline reads 100 %.
- `vibration` is sent in mm/s, estimated as a_rms / (2π·f_rot) with `FAN_RPM` from the
  sketch. This assumes the vibration is dominated by the 1× rotation frequency, as with
  imbalance. The network itself works on the acceleration ratios.
- If the INA219 or MAX6675 is not wired yet, the sketch sends simulated constant values
  and the network sees that sensor at its baseline.
- `temp_score`, `current_score` and `vibration_score` show how much health is lost when
  only that sensor deviates. This tells the technician *why* the alert fired.
